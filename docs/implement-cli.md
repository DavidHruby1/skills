# Implement CLI

Run `implement task-001` inside the target Git repository. The CLI uses `stage` as the integration branch and operates on exactly one repository. It is separate from `/implement`, which retains its existing multi-repository PLAN.md workflow. Bun, OpenCode, Git, and authenticated `gh` or `glab` must be available. The `~/.local/bin` directory must be on `PATH`.

The task must contain `.opencode/tasks/task-001/PROPOSAL.md` and `SPEC.md` with `Status: accepted` (or `**Status:** accepted`). Planning reads both complete documents and relevant source. The planner writes a detailed, schema-validated, one-phase-per-PR `execution.json`, including exact production ownership, read-first symbols, ordered implementation steps, acceptance, invariants, protected test paths, setup commands, and test/typecheck commands. The script fixes branch IDs, parent targets, worktree paths, base SHA, and document hashes. Inspect `execution.json` before executing a task with repository- or dependency-changing setup commands: the command screening is not a security sandbox. Do not change this file once execution starts; stop and reconcile state manually instead.

After issue reconciliation (parent plus one issue per phase with `opencode-task` and task-ID labels), each phase runs sequentially in a dedicated stacked worktree. The existing `worker` receives a standalone bounded production assignment; it cannot inspect tests or run Git. The CLI executes the planned checks directly in that phase's worktree, diagnoses production failures, and asks the same worker to repair them (at most three corrections). It stages only owned paths and commits only after passing checks. It does not write tests. Setup may be needed independently in each worktree; output logs go beside the runtime state under `~/.local/state/opencode/implement/` or `$XDG_STATE_HOME/opencode/implement/`.

After all phases, two independent inspectors perform one full Standards/Spec review. If they find defects, the owning worker fixes them; the script commits and restacks unpublished descendants and reruns affected checks. Later rounds use one inspector to verify the previous findings and review the repairs. At most three review rounds run. If the third round finds defects, the script fixes and tests them, then publishes with an explicit notice that these final corrections were not independently re-reviewed. Publication uses the unchanged create-pr skill one explicit branch at a time: first PR targets the integration branch, later PRs initially target their predecessor. Ticket-master links each published URL to its slice issue. Neither merges nor retargets PRs.

`execution.json` is the immutable execution authority; the state file outside the repository records session IDs, Git checkpoints, issue URLs, validation fingerprints, review rounds, and PR URLs. Repeat the same command to resume. Changes to the spec, proposal, base commit, or plan block resumption rather than silently rewriting branches. Git conflicts, unexpected dirty/unowned files, missing access, and uncertain provider writes stop with the worktrees preserved for inspection; never force-push, reset, stash, or clean them automatically. Review/merge the stack bottom-up, then retarget successors to the integration branch after their predecessor merges.
